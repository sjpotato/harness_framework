# Architecture Decision Records

## 철학
서버 없는 최소 구현 우선. 로그인·저장·공유처럼 "있으면 좋은" 기능은 전부 MVP에서 제외하고, URL 입력부터 리포트 확인까지 한 화면 흐름만 완성한다. 단, 에러/엣지 케이스 처리는 범위를 줄이지 않는다 — 기능은 최소화하되 있는 기능은 견고하게 만든다.

---

### ADR-001: 서버 없는 순수 프론트엔드 SPA
**결정**: 백엔드/API 라우트/DB 없이 React + Vite + TypeScript 정적 SPA로 만든다. 모든 외부 API(YouTube Data API, Claude API)는 브라우저에서 직접 호출한다.
**이유**: 로그인도, 리포트 저장도 필요 없는 "그 자리에서 한 번 보고 끝"인 도구이므로 서버를 운영할 이유가 없다. 정적 호스팅만으로 배포·유지보수 비용이 0에 가깝다.
**트레이드오프**: API 키를 서버에 숨길 수 없어 사용자가 직접 자기 키를 입력해야 한다(ADR-002). 요청 로깅·요율 제한·캐싱 같은 서버 사이드 최적화를 포기한다.

### ADR-002: API 키는 사용자 입력 + localStorage 저장
**결정**: YouTube Data API 키, Claude API 키를 앱에 하드코딩하거나 서버에 보관하지 않는다. 사용자가 설정 화면에서 직접 입력하고, 브라우저 `localStorage`에만 저장한다. 로컬 개발 편의를 위한 `.env.local` 값이 있어도 이는 개발자 본인 환경에만 존재하며 git에 커밋하지 않는다.
**이유**: 서버가 없으므로(ADR-001) 키를 안전하게 숨길 위치가 없다. 앱을 공개 배포해도 운영자의 키가 노출되지 않으며, 각 사용자가 자기 키의 요금·쿼터를 직접 책임진다.
**트레이드오프**: 사용자가 YouTube Data API 키와 Anthropic API 키를 직접 발급받아야 하는 진입장벽이 생긴다. 키가 브라우저에 평문 저장되므로 공용 PC 사용 시 주의가 필요하다(설정 화면 안내 문구로 대응).

### ADR-003: 감정분석·피드백 생성은 Claude API에 위임
**결정**: 댓글 감정분석과 강점/개선점 피드백 생성을 자체 로직이나 로컬 라이브러리가 아닌 Claude API 호출로 처리한다.
**이유**: 한국어를 포함한 다국어 댓글의 뉘앙스를 파악하고, 정형화된 수치(비율)와 비정형 피드백(문장)을 동시에 생성해야 하므로 규칙 기반/경량 라이브러리보다 LLM이 압도적으로 적합하다.
**트레이드오프**: 분석할 때마다 API 비용이 발생하고, Claude API 응답 지연(수 초)이 리포트 생성 시간에 그대로 반영된다. 오프라인에서는 동작하지 않는다.

### ADR-004: 댓글 수집은 최대 100개, 페이지네이션 없음
**결정**: YouTube Data API의 `commentThreads.list` 1페이지(최대 100개, 관련순)만 가져온다. 대댓글도 수집하지 않는다. 그 이상은 MVP에서 다루지 않는다.
**이유**: 소규모 채널 기준 대표성 있는 샘플을 빠르고 저렴하게 얻을 수 있고, Claude API에 보낼 프롬프트 길이와 토큰 비용도 예측 가능한 범위로 유지된다.
**트레이드오프**: 댓글이 아주 많은 인기 영상에서는 표본이 실제 여론을 완전히 대표하지 못할 수 있다. 리포트에 실제 수집 개수를 항상 표기해 사용자가 표본 크기를 인지하게 한다(PRD.md). 추후 필요 시 페이지네이션을 별도 기능으로 추가할 수 있다.

### ADR-005: 모든 실패는 AppError 타입 계층으로 정규화 후 UI에 전달
**결정**: `services/` 레이어에서 발생하는 모든 실패(HTTP 상태 코드, 네트워크 오류, 파싱 실패)를 `AppError`라는 판별 유니온(discriminated union)으로 변환한 뒤에만 컴포넌트로 전달한다. 원본 `fetch`/에러 객체를 컴포넌트까지 그대로 넘기지 않는다.
**이유**: PRD.md에 정의된 15개 이상의 에러/엣지 케이스를 각각 다른 문구로 보여줘야 하는데, raw 에러를 그때그때 분기하면 케이스 누락이 생기기 쉽다. 타입으로 강제하면 새 에러 케이스 추가 시 컴파일 타임에 매핑 누락을 잡을 수 있다.
**트레이드오프**: `services/` 레이어에 에러 매핑 보일러플레이트가 늘어난다. 예상하지 못한 새로운 API 에러 코드가 오면 별도 fallback 케이스가 필요하다.

### ADR-006: 댓글 원문은 텍스트로만 렌더링 (dangerouslySetInnerHTML 금지)
**결정**: 유튜브 댓글 원문을 화면에 표시할 때 React의 기본 텍스트 노드 렌더링만 사용한다. HTML 파싱/렌더링을 하지 않는다.
**이유**: 댓글은 사용자 생성 콘텐츠(UGC)라 스크립트나 HTML 태그가 섞여 있을 수 있다. 서버가 없어 별도 새니타이징 레이어를 둘 수 없으므로, 애초에 HTML로 해석하지 않는 것이 가장 단순하고 확실한 XSS 방지책이다.
**트레이드오프**: 댓글에 포함된 링크가 클릭 가능한 하이퍼링크로 표시되지 않는다(일반 텍스트로만 보임). MVP에서는 허용한다.

### ADR-007: Claude 응답은 구조화 출력 요청 + 파싱 실패 시 1회 재시도
**결정**: Claude API 호출 시 응답이 정해진 JSON 스키마를 따르도록 명시적으로 지시하고, 클라이언트에서 파싱/스키마 검증에 실패하면 동일 요청을 1회 재시도한다. 재시도 후에도 실패하면 에러로 처리한다.
**이유**: LLM 응답은 형식이 흔들릴 수 있어 파싱 실패가 드물지 않게 발생한다. 무한 재시도는 비용·지연을 키우므로 1회로 제한해 실패를 사용자에게 빠르게 알리는 쪽을 택한다.
**트레이드오프**: 재시도 1회로도 실패하는 극소수 케이스는 사용자가 직접 "다시 시도"를 눌러야 한다. 재시도 시 API 비용이 두 배로 들 수 있다.

### ADR-008: 데스크톱 우선, 모바일 반응형은 MVP 범위 밖
**결정**: 레이아웃은 데스크톱 뷰포트 기준으로 설계한다. 모바일에서 완전히 깨지지 않는 정도(레이아웃 붕괴 방지)만 보장하고, 별도 모바일 최적화 작업은 하지 않는다.
**이유**: 크리에이터가 댓글 반응을 확인하는 작업은 주로 데스크톱에서 이루어진다고 가정했고, MVP 범위를 최소화하기 위해 반응형 튜닝에 리소스를 쓰지 않기로 한다.
**트레이드오프**: 모바일 사용성이 최적은 아니다. 실사용 피드백에 따라 이후 버전에서 반응형을 추가할 수 있다.

### ADR-009: 외부 API 호출에 고정 타임아웃 + 수동 재시도만 적용
**결정**: YouTube API 호출은 10초, Claude API 호출은 30초로 타임아웃을 고정한다. 네트워크 오류·타임아웃·rate limit(429)은 사용자가 직접 누르는 "다시 시도" 버튼으로만 재시도하며, 자동 백오프 재시도 로직은 두지 않는다.
**이유**: 서버가 없어 재시도 정책을 중앙에서 조정할 수 없고, 자동 재시도는 API 비용(특히 Claude)을 사용자 모르게 늘릴 수 있다. 수동 재시도가 더 예측 가능하고 사용자에게 통제권을 준다.
**트레이드오프**: 일시적 네트워크 문제에도 사용자가 직접 버튼을 눌러야 하는 불편이 있다.

### ADR-010: 댓글 수집 전 videos.list로 영상 메타데이터·상태를 먼저 확인
**결정**: `commentThreads.list`를 바로 호출하지 않고, 그 전에 `videos.list`를 먼저 호출해 영상 존재 여부·공개 상태·댓글 활성화 여부를 확인하면서 동시에 리포트에 표시할 제목·썸네일을 확보한다.
**이유**: (1) `commentThreads.list`의 에러 코드만으로는 "영상 없음"/"비공개"/"댓글 비활성화"를 안정적으로 구분하기 어렵다. `videos.list` 응답이 이 구분을 명확하게 제공한다. (2) 리포트 화면에 분석 대상 영상을 식별할 제목·썸네일이 반드시 필요한데(사용자 경험 리뷰에서 발견 — 리포트만 봐서는 어떤 영상인지 알 수 없는 문제), 이 메타데이터를 별도로 또 요청하는 것보다 에러 검증과 한 번에 처리하는 게 효율적이다.
**트레이드오프**: API 호출이 1회 늘어나 왕복 지연이 조금 증가하고 YouTube API 쿼터를 영상당 1 unit 더 소비한다(무료 쿼터 규모를 감안하면 실질적 영향은 미미).

### ADR-011: 진행 중인 요청은 AbortController로 취소 가능하게 하되, Claude 호출은 "화면만 되돌리기"로 처리
**결정**: 댓글 수집·분석 진행 중 "취소" 버튼을 누르면 `AbortController.abort()`로 진행 중인 fetch를 중단하고 즉시 URL 입력 화면으로 되돌린다. 단, Claude API 요청은 취소 시점에 이미 Anthropic 서버에 도달해 처리 중일 수 있으므로, 실제로는 응답을 기다리지 않고 화면만 전환하는 것이며 서버 측 처리(및 과금)를 막지는 못한다.
**이유**: 잘못된 URL을 넣었거나 마음이 바뀐 사용자가 새로고침(전체 리셋) 없이 빠르게 다른 작업으로 넘어갈 수 있어야 한다는 사용자 경험 요구가 있었다. 완벽한 취소(서버 처리 중단)는 서버가 없는 아키텍처에서 애초에 불가능하므로, 가능한 범위(클라이언트 대기 중단)까지만 구현하고 그 한계를 사용자에게 안내한다.
**트레이드오프**: "취소"가 Claude 단계에서는 진짜 취소가 아니라 "결과를 안 기다리기"에 가깝다는 점이 사용자에게 완전히 직관적이지 않을 수 있다. UI 카피로 이 한계를 분명히 전달해야 한다(PRD.md 참고).
